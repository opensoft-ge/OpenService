## Cycle 1 — private browser-session inventory (OS-F10-01)

**Base:** `18bd066`. **Scope:** ADOPT-08, OS-PARITY-08/10; blueprint A2 personalization and A4 authentication. The prior implementation exposed only all-browser revocation and had no per-session inventory.

**Feature:** schema 21 stores random public IDs and SHA-256 hashes of servlet session IDs, account/revision, sign-in/last-activity/absolute-expiry timestamps. Successful sign-in registers one entry and replaces a prior entry for the same cookie. Logout deletes it. Authenticated cookie use checks identity, revision, clock bounds, 30-minute idle and eight-hour absolute expiry and updates activity; missing pre-upgrade entries fail closed. Heartbeats commit before business-write locks. `GET /account/sessions` and `GET /api/openservice/me/sessions` expose only the caller's valid entries, a current-browser marker, UTC times and `truncated`; newest 100 rows maximum. Unknown queries/methods fail. Basic credentials do not create a browser entry. Existing sign-out-all and credential/role revocation continue to invalidate entries through account revision.

**Acceptance:** independent cookie jars, identity isolation even with a different Basic principal, hashed-only persistence, repeated-login replacement, logout removal, idle/absolute/future-clock boundaries, missing registration denial, durable inventory reinitialization, upgrade rollback/replay on SQLite and PostgreSQL, API method/query rejection, bounded output and keyboard/axe/overflow browser checks in both themes.

**Limits:** inventory is not distributed servlet storage or proof a browser is still open. Closed browsers and entries from an application restart remain until idle/absolute expiry; the page explains this. No IP address or user-agent collection, individual termination, session extension or automatic concurrency limit in this slice. An overflow is visible and all-browser revocation remains available.

**Discovery:** [Brazil active sessions](https://www.servicenow.com/docs/r/platform-security/identity/active-sessions.html) and [Brazil session administration](https://www.servicenow.com/docs/r/platform-administration/user-administration/c_ManageUserSessions.html), updated 10 September 2026, retrieved 15 November 2026, support session visibility/termination as reusable foundations. [OWASP session guidance](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), retrieved the same day, informs local lifecycle boundaries. Newly tracked OS-DISC-SESSION-LIMIT: [Brazil concurrent session limits](https://www.servicenow.com/docs/r/platform-security/authentication/explore-lcs.html), missing P1/M1 under ADOPT-08/OS-PARITY-08; depends on session registry and administrator policy; acceptance must prove atomic oldest-session eviction and bounds under simultaneous sign-ins. Vendor feature requires its concurrent-session plugin; no such plugin compatibility is claimed. Candidate alternatives: scoped API credentials and SSO/MFA remain higher-level identity gaps. Rotating discovery attempted authentication/identity release-note pages (404); identifier-first routing remains unverified and merged into the existing SSO backlog, not claimed as supported. Next research: individual session termination and API authentication policy.

**QA ledger:** review 1 corrected heartbeat-row/advisory-lock inversion before gates and made schema creation replay-safe; targeted tests passed after fixing a checked-exception compilation omission. Review 2 found an out-of-order heartbeat race: a later-sampled timestamp could make an earlier in-flight request appear invalid. Activity now advances monotonically using an atomic SQL expression; a regression verifies reverse arrival order without session loss. The in-progress full gate was stopped and will be rerun cleanly. Review 3: the full run passed both workflow suites and 38 browser journeys but exposed two failures in the existing approval-upgrade fixture, which deleted only migration 20 and assumed 20 was latest. The fixture now removes all later history and asserts the current version after upgrading, preserving its exact version-19 rollback assertion. The new session-upgrade fixture follows the same convention. Review 4 rechecked the complete diff against `18bd066`, including previous repairs, login/logout callers, account-revision guards, SQL rollback/replay and both-theme screenshots. It found no new or reopened defects and made no repairs. The final clean full gate passed.

**Completed cycle 1.** Final clean gate: 541 tests, zero failures/errors/skips; Java 4573/4573 lines, 2437/2437 branches, 270/270 methods. Exact per-file Java and JavaScript gates pass. Browser migration: 75/75 lines, 49/49 branches, 12/12 functions; theme: 36/36 lines, 15/15 branches, 6/6 functions. ## Cycle 2 — end one browser session (OS-F10-02)

**Base:** `24a6f14`. **Scope:** ADOPT-08/09, OS-PARITY-08, blueprint A2/A4. Inventory existed after cycle 1, but could only be acted on using all-browser revocation. Alternatives retained: concurrent-session policy, scoped credentials and SSO/MFA.

**Feature:** `POST /api/openservice/me/sessions/{session_id}/revoke` with `{}` ends only an entry belonging to the authenticated account and returns `{result:{revoked:true,current:boolean}}`. The account inventory has matching CSRF-protected forms. Ending this browser redirects to login; ending another returns to the inventory. The transaction writes an `account.session_revoked` event containing only the public session ID. Missing, other-account and repeated IDs yield 404; unknown query/body fields fail. Reader/requester accounts can manage their own sessions. Basic credentials remain usable. Cookie-authenticated mutations recheck session validity after acquiring the shared write lock, without releasing it.

**Acceptance:** two independent browsers, cross-account denial, invalid CSRF/body/query/method, current and other-session paths, simultaneous same-session revocation (one success and one 404, one event), rollback retaining the session and removing the uncommitted event. A real PostgreSQL HTTP write waits on the advisory lock while its session is revoked, then returns 401 without creating its incident. Chromium exercises keyboard termination, surviving other sessions, current-browser logout and re-login, axe checks and desktop/mobile in both themes.

**Evidence/discovery:** [session administration](https://www.servicenow.com/docs/r/platform-administration/user-administration/c_ManageUserSessions.html) and [Identity Center sessions](https://www.servicenow.com/docs/r/platform-security/identity/active-sessions.html), retrieved 2026-11-15; current pages are Brazil/2026-09-10, cached search entries still label Australia/2026-03-12. Both describe individual termination; the implementation uses original OpenService routes, not vendor wire compatibility. [Brazil API access policy](https://www.servicenow.com/docs/r/platform-security/authentication/api-access-policy.html), updated 2026-09-10, confirms method/endpoint authentication policy as an additional reusable foundation. Record OS-DISC-API-AUTH-POLICY, missing P1/M1, under ADOPT-08/OS-PARITY-08/03: depends on authentication mechanisms and scoped administration; acceptance must deny disallowed methods across API/export routes and preserve an administrative recovery path. [Brazil new-feature notes](https://www.servicenow.com/docs/r/release-notes/rn-summary-new-features.html), updated 2026-11-04, add delegated AI-agent containment. Merge OS-DISC-AI-CONTAINMENT into OS-PARITY-06, missing P1/M2: requires AI identities, tool authorization and runtime lifecycle; accept only authorized containment, audit it, and prevent subsequent execution. This is discovery only; no AI runtime added. Next research: concurrent session limits and identity policy administration.

**Limits:** no device trust, session extension, MFA or administrator session console. Revocation blocks future authentication and queued writes at the transaction boundary; it does not undo completed actions or promise cancellation of an already authorized external operation.

**QA ledger:** review 1 examined the complete diff, authentication precedence, reader/requester exceptions, ownership query, audit atomicity, transaction lock lifetime and browser forms. It added concurrent-repeat and rollback assertions before the final gate; no runtime defect required repair. Focused database/browser and queued-write checks passed. Review 2 fixed test-resource close order so the held database lock is released before the executor waits during an assertion failure, and added an explicit requester-login/revocation assertion. Review 3 rechecked the entire accumulated diff against `24a6f14`, including previous test repairs, the post-lock guard, Basic/cookie precedence, current-session invalidation and both-theme browser evidence. ## Cycle 3 — configurable concurrent-browser limit (OS-F10-03)

**Base:** `a33d5d5`. **Scope:** ADOPT-08/09, OS-PARITY-08/10; advances OS-DISC-SESSION-LIMIT, blueprint A4 authentication. Prior sign-ins had no concurrency cap. Alternatives: per-account/role policy, Basic restrictions and SSO/MFA.

**Feature:** `MAX_BROWSER_SESSIONS` defaults to 10 and accepts canonical integer strings 1–100. Invalid values fail startup. A successful login registers its new cookie then, under the existing shared write lock, retains it plus the newest remaining entries for that account/revision. Excess oldest entries are removed with a sanitized `account.sessions_limited` count/maximum audit event in the same transaction. Ties use public session ID ordering. The session page explains the actual limit. Compose already reads the private `.env`; the JAR reads the environment. No secrets or example credentials were added.

**Acceptance:** boundary values 1/100/default, malformed/out-of-range configuration, SQL rollback of eviction and audit on both databases, current-cookie preservation under equal timestamps, unchanged other users and Basic credentials, two simultaneous HTTP sign-ins with exact final counts and audit totals, old-cookie denial, and browser-rendered policy text in both themes. Focused tests passed before the clean full run.

**Evidence/discovery:** [Brazil concurrent session limits](https://www.servicenow.com/docs/r/platform-security/authentication/explore-lcs.html), updated 2026-09-10, retrieved 2026-11-15. This local configurable cap is not the vendor's per-role/plugin implementation or its default. [Brazil release summary](https://www.servicenow.com/docs/r/release-notes/rn-summary-new-features.html), updated 2026-11-04, now verifies identifier-first policy routing as a capability; merge OS-DISC-LOGIN-ROUTING into the existing SSO backlog, missing P1/M1, dependencies: identity providers, safe local recovery and policy administration. Acceptance: deterministic routing, authenticated callback validation and no account-enumeration leak. Detailed linked documentation was unavailable, so exact defaults/conditions remain unverified. The same release summary confirms Basic authentication restrictions; merge that into OS-DISC-API-AUTH-POLICY for the next focused investigation. No SSO or Basic restriction implemented in this cycle.

**Limits:** one deployment setting, no per-user/per-role overrides or unlimited mode. Apply a consistent value to every node; HA/distributed servlet storage is unqualified. Limit enforcement happens on sign-in; this is not a background policy sweep. Existing idle/absolute expiry and user-selected revocation remain separate controls. No MFA claim.

**QA ledger:** review 1 checked configuration parsing/startup, both SQL dialects, current-cookie preservation, lock order, audit atomicity, identity isolation, request race tests and documented environment wiring. No runtime defect identified. Review 2 examined the whole accumulated diff against `a33d5d5`, account/revision SQL predicates, simultaneous-login results, policy display and mobile dark-mode evidence. No new or reopened defects were found and no repairs were made. The clean full gate passed.

## Cycle 4 — per-account Basic authentication control (OS-F10-04)

**Base:** `a999897`. **Scope:** ADOPT-08/09, OS-PARITY-08/03; partial OS-DISC-API-AUTH-POLICY. Existing API-only mode could restrict browser access, but administrators could not block Basic authentication for a browser account. Alternatives: administrator session visibility, endpoint policy and OAuth/SSO.

**Feature:** schema 22 adds `allow_basic`, default true to preserve existing integrations. Administrator GET/POST `/api/openservice/users/{id}/basic-auth` returns/accepts `{allow_basic:boolean}`; the account detail page has an equivalent CSRF-protected control. Actual changes atomically revoke sessions/security links and record `account.basic_access_changed` with before/after booleans; repetitions are idempotent. A blocked header receives the same generic credential failure and throttle handling as other failed authentication, on API, browser and export paths, even if a valid cookie accompanies it. Form sign-in and cookie-authenticated API access remain available with existing permissions. API-only and Basic-disabled cannot be combined through either administration action; concurrent changes serialize. The sole browser administrator can block Basic and recover access through form sign-in.

**Acceptance:** real HTTP allow/block/restore, explicit-header precedence over cookies, old-cookie denial, unchanged record/role enforcement, strict boolean/body/query/method validation, missing accounts, non-admin denial, CSRF, idempotent audit, both-database migration rollback/replay/restart, rollback preserving account revision and audit, simultaneous incompatible policy changes, administrator browser recovery, and real keyboard/desktop/mobile/both-theme controls. Focused tests passed after correcting the new unit fixture to use its actual bootstrap password.

**Evidence/discovery:** [Brazil Basic authentication restrictions](https://www.servicenow.com/docs/r/platform-security/authentication/basic-auth-restriction.html) and [exception inventory](https://www.servicenow.com/docs/r/platform-security/authentication/basic-auth-exceptions.html), updated 2026-09-10, retrieved 2026-11-15. Local per-account allow/block is a bounded original contract, not the vendor's exception-role, tracking-period or scheduled-enforcement implementation. Its documentation identifies a future migration away from Basic; OAuth/mTLS/scoped credentials remain missing here. Wider discovery merges permission-aware retirement/replacement links into the existing knowledge versioning backlog, OS-PARITY-04, missing P1/M2: [Brazil retirement](https://www.servicenow.com/docs/r/servicenow-platform/knowledge-management/retire-versioned-article.html), updated 2026-09-10, retrieved 2026-11-15. Requires published/draft isolation and visibility rules; accept only authorized retirement, exclude retired content from requester search, prevent replacement redirects from revealing restricted articles. [Brazil release summary](https://www.servicenow.com/docs/r/release-notes/rn-summary-new-features.html), updated 2026-11-04, adds SAML certificate-expiry alerts; merge into the existing SSO lifecycle backlog, missing P1/M2, dependent on trusted IdP configuration and delivery, with expiry/replacement/recovery tests. Next research: administrator sessions and knowledge lifecycle.

**Limits:** no global default-deny policy, allowlist roles, per-endpoint rules, tracking mode, OAuth, MFA or token credentials. This controls the HTTP authentication mechanism, not whether browser users may call APIs. Failed blocked attempts use the existing shared sign-in throttle. Changes invalidate current sessions rather than silently preserving previously authenticated authority. Parent parity and M1–M3 remain incomplete.
