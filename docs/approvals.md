# Assigned staff reviews

OpenService records separate review evidence for a proposed state change. It does **not yet require approval before changing a record**, execute approved actions, send notifications or implement quorum/delegation/deadlines. These remain OS-PARITY-02 follow-ups. This is an original local contract, not a replica of ServiceNow endpoints.

From a record, choose **Record approvals**. An administrator or agent requests review from a different active administrator/agent with access and the required state-entry/field-write authority. The reviewer opens the same page and records approval or rejection; rejection requires a comment. Each request captures record revision and configuration version. Editing either makes the proposal outdated and undecidable; request a review of the new revision. All access is checked again when reading or deciding, including state-field read rules, record visibility and the reviewer's current permissions. Deactivation or required credential replacement blocks the account normally; it never implies approval.

## HTTP contract

- `GET /api/openservice/records/{table}/{id}/approvals` returns `result`, `next_before` and `pending_count` for the current record/configuration. Pages contain at most 100 rows in descending creation sequence. Optional `before` is a 32-character approval ID belonging to this record; invalid, missing-from-storage or foreign cursors return 400. Empty/malformed/unknown/repeated parameters fail; cursors confer no authorization.
- `POST` to the same URL requires exactly `expected_revision` (nonnegative integer), `approver` (username), `target_state` and `reason` (nonblank, at most 2000 Unicode code points, no NUL). Returns 201 with `result`. Missing/ineligible reviewer returns 400; stale revision or a duplicate reviewer/target/revision/configuration tuple returns 409. Terminal reviews also reserve that tuple; revise the proposal before requesting that same reviewer again.
- `POST /api/openservice/records/{table}/{id}/approvals/{approval_id}/decision` requires exactly `decision` (`approved` or `rejected`) and `comment` (string up to 2000 code points, no NUL; nonblank for rejection). Returns 200. Only the assigned reviewer may decide (403 otherwise); inaccessible records or approval/record mismatches return 404. Already-decided or outdated proposals return 409. No writes accept URL query parameters.
- Browser equivalents under `/record/{table}/{id}/approvals` use CSRF-protected forms. Both professional themes and keyboard operation use the existing shared controls. Review text is escaped; no JavaScript is required.

Each result includes identity IDs/names, reason/comment, target, status, timestamps, captured revisions and `current`. Internal sequence and credential revision are not exposed. Review text is staff-visible to anyone with access to the record and state field; do not paste credentials or unrelated sensitive data. Audit events contain approval IDs and decision status, without duplicating review text or record payloads. Review decisions do not increment the business-record revision. Comments and attachments have separate journals and also do not increment that revision; this protocol binds the record fields and configuration, not a complete immutable evidence bundle.

Schema 19 introduces `os_approval`. Upgrade is transactional; existing records and credentials are preserved. PostgreSQL mutations share the existing application write lock; SQLite uses immediate transactions. Concurrent duplicate requests or decisions produce one success and one conflict. Rollback removes review and audit together. History persists across restart/backup/restore. Record deletion makes its review history inaccessible through these endpoints; retention/export/reassignment are separate planned capabilities.

Evidence: `ApprovalAcceptance`, `ApprovalTest`, `ApprovalBrowserAcceptance`, the [cycle ledger](paired-cycles-2026-11-15.md), and `scripts/restore-drill.sh`. Sources: [ServiceNow Brazil approvals](https://www.servicenow.com/docs/r/servicenow-platform/approvals/r_Approvals.html), [approval reauthentication](https://www.servicenow.com/docs/r/servicenow-platform/approvals/approval-with-e-signature.html), retrieved 2026-11-15. No electronic-signature compliance or complete workflow parity is claimed.

## Personal queue

Staff can open **My approvals** in navigation or `GET /api/openservice/me/approvals`. Browser route: `/account/approvals`. `status` defaults to `requested`; `approved` and `rejected` are the other accepted values. The response contains `result`, `status` and `next_before`. At most 100 assigned reviews are returned in descending creation sequence, after applying current record visibility and state-field read rules. Each row includes permission-filtered `record_number`, `record_table`, `table_label` and the existing review metadata, with `current` indicating record/configuration freshness. Raw record data and internal sequence/credential revision values are omitted.

Optional `before` is a 32-character review ID assigned to the current account; malformed, unknown or other-account cursors fail 400. A cursor only marks a position and does not confer access. Unknown/repeated query keys and invalid/empty values fail 400. Reader/requester access fails 403; signed-out API access fails 401 and non-GET methods fail 405. PostgreSQL reads use the shared authorization/configuration lock and refresh the caller. State-field restrictions or revoked group membership remove rows immediately; outdated proposals remain visible with a clear explanation. This is a local queue contract, not ServiceNow My Items endpoint compatibility.

Evidence: `ApprovalInboxAcceptance` on both databases, `ApprovalInboxBrowserAcceptance` for navigation, escaped text, decisions, filters, both themes, desktop/mobile accessibility and 100+1 paging.
