# Assigned staff reviews

OpenService records separate review evidence for a proposed state change and can enforce a configured minimum number of current peer approvals before entering a state. Decisions do not automatically execute actions. Notifications, delegation, mandatory named responses and deadlines remain OS-PARITY-02 follow-ups. This is an original local contract, not a replica of ServiceNow endpoints.

From a record, choose **Record approvals**. An administrator or agent requests review from a different active administrator/agent with access and the required state-entry/field-write authority. The reviewer opens the same page and records approval or rejection; rejection requires a comment. Each request captures record revision and configuration version. Editing either makes the proposal outdated and undecidable; request a review of the new revision. All access is checked again when reading or deciding, including state-field read rules, record visibility and the reviewer's current permissions. Deactivation or required credential replacement blocks the account normally; it never implies approval.

## HTTP contract

- `GET /api/openservice/records/{table}/{id}/approvals` returns `result`, `next_before` and `pending_count` for the current record/configuration. Pages contain at most 100 rows in descending creation sequence. Optional `before` is a 32-character approval ID belonging to this record; invalid, missing-from-storage or foreign cursors return 400. Empty/malformed/unknown/repeated parameters fail; cursors confer no authorization.
- `POST` to the same URL requires exactly `expected_revision` (nonnegative integer), `approver` (username), `target_state` and `reason` (nonblank, at most 2000 Unicode code points, no NUL). Returns 201 with `result`. Missing/ineligible reviewer returns 400; stale revision or a duplicate reviewer/target/revision/configuration tuple returns 409. Terminal reviews also reserve that tuple; revise the proposal before requesting that same reviewer again.
- `POST /api/openservice/records/{table}/{id}/approvals/{approval_id}/decision` requires exactly `decision` (`approved` or `rejected`) and `comment` (string up to 2000 code points, no NUL; nonblank for rejection). Returns 200. Only the assigned reviewer may decide (403 otherwise); inaccessible records or approval/record mismatches return 404. Already-decided or outdated proposals return 409. No writes accept URL query parameters.
- Browser equivalents under `/record/{table}/{id}/approvals` use CSRF-protected forms. Both professional themes and keyboard operation use the existing shared controls. Review text is escaped; no JavaScript is required.

Each result includes identity IDs/names, reason/comment, target, status, timestamps, captured revisions and `current`. Internal sequence and credential revision are not exposed. Review text is staff-visible to anyone with access to the record and state field; do not paste credentials or unrelated sensitive data. Audit events contain approval IDs and decision status, without duplicating review text or record payloads. Review decisions do not increment the business-record revision. Comments and attachments have separate journals and also do not increment that revision; this protocol binds the record fields and configuration, not a complete immutable evidence bundle.

Schema 19 introduces `os_approval`. Upgrade is transactional; existing records and credentials are preserved. PostgreSQL mutations share the existing application write lock; SQLite uses immediate transactions. Concurrent duplicate requests or decisions produce one success and one conflict. Rollback removes review and audit together. History persists across restart/backup/restore. Record deletion makes its review history inaccessible through these endpoints; retention/export/reassignment are separate planned capabilities.

Evidence: `ApprovalAcceptance`, `ApprovalTest`, `ApprovalBrowserAcceptance`, the [cycle ledger](paired-cycles-2026-11-15.md), and `scripts/restore-drill.sh`. Sources: [ServiceNow Brazil approvals](https://www.servicenow.com/docs/r/servicenow-platform/approvals/r_Approvals.html), [approval reauthentication](https://www.servicenow.com/docs/r/servicenow-platform/approvals/approval-with-e-signature.html), retrieved 2026-11-15. No electronic-signature compliance or complete workflow parity is claimed.

## Personal queue

Staff can open **My approvals** in navigation or `GET /api/openservice/me/approvals`. Browser route: `/account/approvals`. `status` defaults to `requested`; `approved`, `rejected` and `withdrawn` are the other accepted values. The response contains `result`, `status` and `next_before`. At most 100 assigned reviews are returned in descending creation sequence, after applying current record visibility and state-field read rules. Each row includes permission-filtered `record_number`, `record_table`, `table_label` and the existing review metadata, with `current` indicating record/configuration freshness. Raw record data and internal sequence/credential revision values are omitted.

Optional `before` is a 32-character review ID assigned to the current account; malformed, unknown or other-account cursors fail 400. A cursor only marks a position and does not confer access. Unknown/repeated query keys and invalid/empty values fail 400. Reader/requester access fails 403; signed-out API access fails 401 and non-GET methods fail 405. PostgreSQL reads use the shared authorization/configuration lock and refresh the caller. State-field restrictions or revoked group membership remove rows immediately; outdated proposals remain visible with a clear explanation. This is a local queue contract, not ServiceNow My Items endpoint compatibility.

Evidence: `ApprovalInboxAcceptance` on both databases, `ApprovalInboxBrowserAcceptance` for navigation, escaped text, decisions, filters, both themes, desktop/mobile accessibility and 100+1 paging.

## Withdrawal

POST `/api/openservice/records/{table}/{id}/approvals/{approval_id}/withdraw` with exactly `{"comment":"No longer needed"}`. The original requesting staff account or an administrator may withdraw a pending review while retaining current record access, readable state and table-update permission. A required comment follows the existing 2000-code-point/NUL-free text rules. Browser actions at the equivalent `/record/` path require CSRF and accept only `withdrawal_reason` plus `csrf`. Repeated fields and write query parameters are rejected.

Success returns 200 with terminal `withdrawn` status and a completion timestamp; browser success redirects to history. Missing/mismatched reviews return 404, unauthorized actors 403, malformed input 400 and already terminal reviews 409. Outdated pending reviews can be withdrawn. Withdrawal and decision share the transaction lock, so exactly one can win a race. The original requester/reviewer/reason remain, a separate audit action records the withdrawing actor, and business state/revision do not change. Rollback leaves both review and audit unchanged. Withdrawn reviews leave the pending queue and can be found with `status=withdrawn`.

This does not undo an approved decision, reset a business item to draft, or override a reviewer. A withdrawn review can now be resubmitted using a fresh request, as described below. Withdrawal itself needs no schema change; resubmission uses schema 20. Evidence: `ApprovalWithdrawalAcceptance`, `ApprovalWithdrawalTest`, `ApprovalWithdrawalBrowserAcceptance`; [Brazil recall capability](https://www.servicenow.com/docs/r/order-management/submitting-approval-requests.html), retrieved 2026-11-15, is scoped to Sales CRM Advanced Approval Management and is not a native endpoint compatibility claim.

## Transition prerequisites

A destination state can specify `"min_approvals": 2` alongside its `roles` and `required_fields` in `transition_rules`. The integer range is 0–10; omission or 0 disables this requirement. The initial state cannot require approval. Configuration export/install/preview uses the existing optimistic version contract. Record pages display each configured minimum.

Entering that state requires the minimum number of distinct approved reviewers for the exact current record revision, configuration version and destination. Each must be a different account from the executing account, active staff with current record access and field/transition authority, not awaiting password replacement, and at the same credential revision captured when deciding. Revoked credentials or permissions cannot provide approval authority. Pending, rejected and withdrawn reviews do not count. This minimum-count policy does not add a rejection veto or mandatory named reviewer.

Only the state may change in a protected transition. Save any other changes first, then obtain reviews of that revision. Missing approvals or combined unreviewed changes fail 409 without changing stored fields/revision/audit. The final state update remains explicit and uses existing permissions and revision checks. A subsequent revision cannot reuse its predecessor's approval. Already-stored records in a protected state can still be edited normally; installing a policy does not retroactively require evidence for existing state. Configuration administrators remain trusted policy owners.

The storage checks cover browser/API updates and staged migration promotion. New imports cannot directly create records in protected states; legacy import preview/apply reports a row error (400), while staged preview/apply fails 409 and rolls back. Map imported records to an unprotected state, then obtain the required destination reviews. Source-system approval evidence is not automatically trusted or translated. No schema migration is needed.

Evidence: `ApprovalGateAcceptance` checks both databases, configuration bounds, counts, actor separation, stale record/configuration/credentials, current access, import paths and a PostgreSQL revocation race; `ApprovalGateTest` checks rollback/restart and missing storage targets; `ApprovalGateBrowserAcceptance` checks request → independent decision → explicit transition in both themes. [Brazil Workflow Studio](https://www.servicenow.com/docs/r/build-workflows/workflow-studio/ask-approval-flow-designer.html) and [change approval definitions](https://www.servicenow.com/docs/r/it-service-management/change-management/create-approval-definitions.html), retrieved 2026-11-15, inform the bounded contract without native policy parity.

## Current requirement snapshot

The existing record approvals GET response also includes `record_revision`, `schema_version` and `requirements`. Each outgoing destination has `target_state`, `label`, `required`, `qualifying` and boolean `approval_satisfied`. The same eligibility calculation used when saving excludes the signed-in executor, stale decisions and reviewers who have lost authority. Destinations with no requirement report zero counts and true; a state with no outgoing transitions returns an empty list. The browser review page shows these values in both themes.

This is a read-only snapshot, not permission to execute or a reservation of approvals. Refresh after changes; the actual write rechecks current evidence and all ordinary permissions/field validation. Current record access and state-field readability are required, just as for review history. Internal approval IDs and credential revisions are not added. No schema migration. Evidence: `ApprovalRequirementsAcceptance` on SQLite/PostgreSQL and the expanded `ApprovalGateBrowserAcceptance`.

## Resubmission after withdrawal

Use the existing request form/API to create a fresh review after withdrawal, even at the same record/configuration revision. All normal current permissions, reviewer eligibility and input checks apply. The new review has a new ID, reason and pending status; the old withdrawn row and its audit entry remain intact. At most one **non-withdrawn** request per reviewer/target/record/configuration revision is allowed. Pending, approved and rejected rows still prevent duplicates; this does not undo a rejection or reuse an approval automatically.

Schema 20 transactionally replaces the old all-status unique constraint with a partial unique index. It preserves all row values and sequence positions, including across rollback, restart and PostgreSQL backup/restore. Stop the application and take a consistent backup before upgrading; this is not a mixed-version rolling upgrade. Evidence: `ApprovalResubmissionAcceptance`, `ApprovalResubmissionTest` and the expanded withdrawal browser journey, plus disposable restore/upgrade drills.
