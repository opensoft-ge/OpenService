# API-only accounts

Administrators can restrict a local account to authenticated API routes. Its password, role, record visibility, field-read rules, activation state and required password replacement remain authoritative. This control removes the browser channel; it does not create scoped tokens or grant additional permissions.

`GET /api/openservice/users/{id}/access-mode` returns `200 {"result":{"api_only":false}}` (or true). Administrator POST to the same endpoint takes exactly `{"api_only":true}` or false. Unknown users return 404, invalid bodies/query arguments 400, non-administrators 403, anonymous callers 401, unsupported methods 405. The account-detail page provides a CSRF-protected form at `/admin/accounts/{id}/access-mode`. Real changes revoke sessions and outstanding identity links and emit `account.access_mode_changed` with only before/after booleans. Repeated requests do not revoke again or duplicate audit.

An API-only account receives the ordinary generic sign-in failure from the browser login form. These attempts count toward the existing shared authentication limit, even with the correct password. Basic-authenticated requests to private non-API paths return 403. Existing sessions are rejected on their next request after mode change. Public static, health and identity-link routes remain public and retain their own validation. Valid password recovery remains possible; it never grants browser access. A required password replacement must be completed through the password-change API or valid recovery before ordinary APIs resume. Changing back to Browser and API permits a fresh sign-in and cannot revive an old session.

At least one active browser-enabled administrator must remain. Mode, role and activation changes share the account-administration lock and enforce this invariant, even if other API-only administrators exist. In-flight requests may complete. This does not prove that any administrator has access to their credential or recovery address.

Schema 18 adds `os_user.api_only`, default false, preserving existing accounts, credentials and required-change state. Quiesce old application nodes during upgrade: old binaries do not enforce this restriction. Keep the flag in backups and verify behavior after restore. SQLite/PostgreSQL acceptance covers upgrade, restart, rollback, concurrency, all roles and interaction with password replacement. Browser acceptance covers mode changes, revocation, denied login and fresh sign-in after restoration, with desktop/mobile light/dark checks.

Current boundaries: dedicated organization per deployment; no OAuth/client credentials, per-integration token scopes, API key rotation, IP restrictions, machine identity provisioning or automatic connector configuration. This local extension is informed by ServiceNow's Brazil non-interactive sessions documentation, not a claim of equivalent protocol support or vendor endpoint conformance.
