# Verified recovery-email enrollment

Existing local accounts without an email address can enroll one through **Account security → Recovery email** (`/account/email`). All active roles, including reader and requester, can manage their own enrollment. Confirm the current password, then follow the single-use link delivered to the proposed address. The address remains unset until an explicit confirmation POST; merely viewing the link does not consume it. Confirmation verifies the address and revokes all existing browser sessions. Sign in again with the unchanged username and password. The existing forgot-password flow can then use this verified address.

## Local API and state contract

- `GET /api/openservice/me/email`: `result` contains the caller's `email`, boolean `verified`, and either `pending: null` or their unconfirmed email/ISO expiry. No token, token hash or other account's details are returned. An expired or invalidated request may remain listed as unconfirmed until replaced/cancelled; its link is unusable.
- `POST /api/openservice/me/email`: exactly `email` and `current_password`; returns 202 with private `result` and `issued` containing a delivery ID and ISO expiry. Email follows the same normalized validation/uniqueness policy as invited users. The link is sent only through the encrypted durable outbox and is not returned to the caller. JSON or browser entry points require authentication; browser writes require CSRF.
- `DELETE /api/openservice/me/email` with `{}` cancels a pending enrollment, returning 200. Browser uses its **Cancel email verification** POST button. Cancellation clears the proposed address/expiry, invalidates the link and preserves the resend timer. It does not remove a verified email or recall already accepted SMTP mail.
- `GET /verify-email/{token}` previews the bound account/address; CSRF-protected POST confirms it and redirects to login. Links expire after 30 minutes, use a stored digest, are bound to the account security revision, and fail after cancellation, replacement, deactivation or credential/session-revision changes. Expired/unavailable/replayed links return 400; an address claimed by another account before confirmation returns 409.

New requests replace old links. At least one minute must elapse between requests, including after cancellation. Current-password verification uses persistent authentication-attempt limits (five failures in the existing five-minute window); successful authentication follows the existing reset policy. Reauthentication commits attempt evidence before enrollment mutation, then reacquires the mutation lock and rechecks the original authenticated revision under the account row lock. A full outbox rolls back the pending request and its lifecycle audit. Delivery-disabled installations return 503 for enrollment requests.

Email must be absent on the account. This flow deliberately rejects changing an existing address with 409, including legacy unverified addresses; replacing a registered address needs a distinct confirmation/recovery policy. No domain ownership, real-world identity, SSO, MFA or managed-provider enrollment is established by an email link.

## Persistence and operation

Schema 15 adds `os_email_enrollment`, one current enrollment/timer per account. Cancel/confirm are serialized with the account lifecycle; confirmation is atomic and single-use under concurrent requests on SQLite and PostgreSQL. Restart preserves requests and outbox payloads. Security events record request, cancellation and confirmation without addresses, passwords or links. The public delivery directory supports `kind=enrollment` mapped to `email.enrollment`; sender payload and address stay private. As with other account messages, delivery is at-least-once and the worker checks current link validity before sending.

Upgrade from schema 14 preserves identities and password hashes. The disposable restore drill includes pending enrollments and their encrypted queued messages for schema 15 sources. Restoring an older database creates the new table through the ordered migration. This is a local implementation, not a ServiceNow Password Reset API or six-digit code compatibility claim.
